# P0: メモリアーキテクチャ決定(2026-09-07)

GOAL.md R1(G-RAM をどこに置くか)への回答。**P3(GDC)着手前の必須決定。**

---

## 1. 結論

| 決定 | 内容 |
|---|---|
| **D-1** | **G-RAM は BRAM に置く。SDRAM は使わない。** |
| **D-2** | **まず 1 ページ(640×400×4プレーン = 100 M10K)で実装する。** |
| **D-3** | プレーン RAM は**ページベースレジスタ経由でアドレスする**。2ページ目の追加をパラメータ変更で済ませる。 |
| **D-4** | **OSD フレームバッファを縮小して余裕を先に確保する**(640×200×4bpp → 320×200×4bpp、+32 ブロック)。 |
| **D-5** | 漢字フォント・OPNA の ADPCM/リズムは **SDRAM 常駐**(BRAM は ANK とキャッシュのみ)。 |

D-1 は**選択の余地がない**(§3)。D-2 は容量の制約(§4)。

## 2. ボトルネックの正体

「M10K が足りない」の内訳を B0 の fit レポートで実測した結果、
**逼迫の主因は PC-98 機械層ではなく、シャーシ側の設定だった。**

| 使用者 | M10K | 内訳 |
|---|---:|---|
| `softcpu_subsystem` | **110** | **OSD フレームバッファ 64** / firmware ROM 32 / 作業RAM 8 / その他 6 |
| `CHIPSET`(PC/AT 機械層) | 47 | IDE dpram 16 / OPL2 9 / その他 22 |
| `i8088` | 16 | |
| `pocket_video` | 10 | |
| その他 | 10 | |
| **合計** | **193 / 308** | |

- **OSD フレームバッファ = 640×200 @ 4bpp = 62.5KB で 64 ブロック。**
  設計全体で単一最大の BRAM 消費者であり、**PC/AT 機械層 47 ブロックより大きい。**
- **firmware ROM は 24KB 確保して 17.6KB しか使っていない**(4,407/6,144 ワード)。

→ **削減余地は機械層ではなくここにある。**

## 3. なぜ SDRAM に置けないか(D-1 の根拠)

`KFSDRAM.sv` の実測パラメータ:

| 項目 | 値 |
|---|---|
| データ幅 | **16 bit** |
| クロック | **42.95 MHz**(`SDRAM_CLK = clk_chipset`) |
| CAS レイテンシ | 2 |
| ポート数 | **1(CPU メインRAM と共有)** |
| 構造 | **アクセスごとに PRECHARGE**(`IDLE→READ/WRITE→PRECHARGE_WAIT→PRECHARGE`)。バンクインターリーブもパイプラインもなし |

理論ピークは 16bit × 42.95MHz = 85.9 MB/s だが、
**上記のとおりランダムアクセスは行ごとにプリチャージが入るため実効は一桁 MB/s 台。**

これに対し G-RAM を SDRAM に置いた場合の要求:

| 用途 | 帯域 | 性質 |
|---|---:|---|
| 表示リフレッシュ(640×400×4プレーン @60Hz) | 7.7 MB/s | シーケンシャル |
| EGC 全画面 read-modify-write @60Hz | 約 15 MB/s | **ランダム** |
| CPU メインRAM アクセス | 常時 | **同じ1ポートを奪い合う** |

→ **実効帯域と同オーダーの要求を、CPU と共有の単一ポートに載せることになる。
D5(EGC 使用タイトルが正速)と両立しない。**

※ 「2ページ目だけ SDRAM に置いてフリップ時にコピー」も不可。
128KB のコピーは実効帯域で 1 フレーム相当を丸ごと消費する。

**したがって G-RAM は BRAM 一択。**

## 4. 容量収支(D-2 の根拠)

M10K 総数 **308**。

### 固定で残るもの

| 項目 | M10K |
|---|---:|
| シャーシ(V30 16 / pocket_video 10 / bridge 2 / その他 8) | 36 |
| `softcpu_subsystem`(現状のまま) | 110 |
| **機械層に使える残り** | **162** |

### PC-98 機械層の要求

| 項目 | サイズ | M10K |
|---|---:|---:|
| **G-RAM 1ページ**(640×400×4プレーン) | 128,000 B | **100** |
| TVRAM(コード 8KB + アトリビュート 8KB、デュアルポート) | 16 KB | 13 |
| ANK フォント(8×16×256)+ 漢字キャッシュ | 20 KB | 16 |
| FDC セクタバッファ(1024B/sect ×2)+ GDC FIFO ほか | — | 10 |
| OPNA 演算ワーク(ADPCM/リズム本体は SDRAM) | — | 5 |
| **合計(1ページ)** | | **144** |
| **合計(2ページ)** | | **244** |

- **1 ページ: 144 / 162 → 収まる(余裕 18)** ✅
- **2 ページ: 244 / 162 → 82 ブロック不足** ❌

### 2ページを載せるための削減余地(それでも足りない)

| 施策 | 削減 |
|---|---:|
| OSD FB 640×200×4bpp → 320×200×4bpp | +32 |
| OSD FB をさらに 320×100 まで縮小 | (+16) |
| firmware ROM 24KB → 20KB | +6 |
| **現実的な最大削減** | **+54** |

→ 216 available vs 244 required。**2ページは依然として 28 ブロック不足。**

**結論: 2ページ構成は本アーキテクチャでは載らない。**

   ローカルに残っていないソースツリーに基づく記述)
- 解消手段: NP2kai のソースを取得して VRAM サイズ/ページ制御レジスタを確認する。
  **ネットワークが要る**(DNS 故障中のため `scripts/tools/ghlib.py` の
  dig ピン留め経路を使う)。

**もし 2 ページが必須と判明した場合**、本アーキテクチャでは
D5(EGC 正速)と D7(全部入り単一ビットストリーム)のどちらかを
諦める必要がある。**その場合はゴールの再交渉が必要**であり、
P3 に着手してから判明すると手戻りが大きい。**だから P0 で潰す。**
