## 1. ★現在位置(2026-09-08 夕)

### 1.0 確定: **CPU が `F000:D880` から取り込むデータが化けている**

バスを覗く受動モニタ(`post_monitor.sv`)で、CPU が `F000:D880` から
読んだ生バイトを捕まえた。

> ⚠️ 「**読み出し経路**が犯人」とまでは**まだ言えない**。
> メモリが最初から間違った値を持っている可能性(BIOS ロード時の取りこぼし)が
> 同じくらい有力で、§1.3 の形はむしろそちらを示唆する。§1.3b で決着させる。

| | D880 | D881 | D882 | D883 |
|---|---|---|---|---|
| BIOS イメージの実体 | `F8` | `2E` | `E8` | `D2` |
| **CPU が読んだ値** | `F8` | `2E` | **`41`** | **`D6`** |

CPU は同じ経路で**命令もフェッチしている**ので、これは下流の症状ではなく原因そのもの
(メモリの中身が悪いのか、読み方が悪いのかは別問題 — §1.3b)。

再現性あり: 別の実行でも `WROTE F000:412E` が2回とも同じ値だった
(POST 05 の `movsw` が `E82E` のはずの所に `412E` を書く。上位バイトが `E8`→`41`)。

**ここまでで潰れた説:**

- **アドレスのエイリアスではない** — `41 D6` という並びは 64KB イメージのどこにも無い。
  他の番地のデータが返っているのではない。
- **DQ レーンの入れ替わり/固着ではない** — ワード `D880`(`F8 2E`)は完全に正しく、
  ワード `D882` は**両バイトとも**壊れている。レーン故障なら前のワードも壊れる。
- **バンク/ロウのマッピングではない** — §1.1 参照。
- **ローダの書き込みカデンスでもない** — §1.1 参照。

### 1.1 アドレスマッピング(実測で確定)

`RAM.sv` は 1 PC バイトを **SDRAM の 16bit ワード1個**に割り当てる
(`access_address = {7'h00, latch_address}`、`access_num = 1`、データは下位8bit)。
`sdram_kf_shim` の `ADDR_BITS` は 9+13+2 = 24 で、**バイトアドレスがそのままワードアドレス**。

`sdram_mp` の写像は `{row, bank, col}` = `addr[23:11]`, `addr[10:9]`, `addr[8:0]`。したがって:

| 番地 | row | bank | col |
|---|---|---|---|
| `FD880` | 507 | 0 | 128 |
| `FD881` | 507 | 0 | 129 |
| `FD882` | 507 | 0 | **130** |
| `FD883` | 507 | 0 | 131 |

**正しいペアと壊れたペアの間にロウ境界もバンク境界も無い。**
「ロウのアクティベートが間に合わずセンスアンプの古い内容が出る」説はここで消える。

### 1.2 シミュレーションのカバレッジ穴 — 塞いだが、再現しなかった

`tb_ram_ab` / `tb_ram_ab_ph` が通っていた理由の一部は**見ている場所**だった。
上の写像だと `0x01000` の 512 バイトも `0x02000` の 256 バイトも
**バンク0の1ロウの中に丸ごと収まる**。つまり「RAM.sv 統合が PASS」は
バンク切り替えもロウ跨ぎも BIOS の番地も一切保証していなかった。

追加した2フェーズ(両ベンチ):

1. `0xFD800` から 2KB — バンク境界4回とロウ境界1回を跨ぎ、`0xFD880-83` を含む。
   不一致は row/bank/col つきで表示する。
2. **BIOS ローダのカデンス** — `core_top` の `bios_load_state` 02〜04 をそのまま写した
   (`ram_rw_complete` まで書き込みを保持 → 5クロック整定 → 次のバイト)。
   イメージはこの経路(チップセットの ext マルチプレクサ → 同じ `RAM.sv` ポート)で
   書かれるので、リフレッシュ衝突で書き込みが落ちるならここに出る。

**結果: `sdram_mp` は全部 PASS。理想タイミングでも基板タイミングでも
違反0・データ誤り0。** → 故障は機能モデルでは到達できない。**電気的な側**に絞られた。

> ローダのカデンスのフェーズは `SDRAM_USE_MP` 側でだけ走らせている。
> `core_top` の実カデンスで **KFSDRAM はモデルに対し tRP 違反を 41 回出す**
> (データは正しく読めている)。KFSDRAM は実機で起動する側なので、
> これはモデルの `T_RP=2` が部品より厳しいか、リファレンスが元々切っている角。
> **既知良品のリファレンスを落とす刺激は、悪い刺激**というこのベンチの規約に従い、
> 記録するがゲートにはしない。

### 1.3 ★壊れ方の「形」— 16バイト窓の結果(run#102)

```
実体   F8 2E E8 D2  EF 50 E3 F2 | E6 6E FE 53  FF 53 FF A4
CPU    F8 2E 41 D6  EF 50 E3 F2 | E6 6E FE 53  FF 53 FF A4
            ^^ ^^                                          N 16
```

**16バイト中、壊れているのは `D882`/`D883` の1ワードだけ。**
同じループが順に読んだ前後14バイトは完璧。

これが効く: **setup マージン不足なら散発的・データ依存にバラける**はずで、
この形にはならない。そして壊れている単位が **16bit ワードちょうど**。
BIOS ローダは 16bit 単位で書く(`bios_write_data <= {8'hFF, bios_write_data[15:8]}`
で2バイトずつ、`core_top.sv` の `bios_load_state` 02〜04)ので、
**ローダが1ワード取りこぼした**なら形が完全に一致する。

### 1.3b 次の一手: メモリが壊れているのか、読み出しが壊れているのか

同じ4バイトを **ext ポート**(CPU とは別経路)から読み直して並べる(`MEM` 行、run#105)。

| `MEM` | 結論 |
|---|---|
| `41 D6` | メモリが実際に壊れている → **BIOS ロードが犯人**、読み出しは無罪 |
| `E8 D2` | メモリは正常 → **CPU の読み出し経路が犯人** |
| 6バイト全部おかしい | 計測器(ext リード)が壊れている。セルフテストマスタの `ROM 11 11 ...` と同じ症状 |

`D884`/`D885` も読むのは、CPU 側で正しいと分かっている2バイトを対照に置くため。

> ⚠️ `guest_peek` はバスを奪う。増やした6アクセスは、
> INT 1Ah ベクタ(表示していない)とスクラッチ往復8バイト(毎回 0/8)を削って払った。
> **前のビルドより14回少ない**。

### 1.3c ✗ 外れた対策: PLL 位相 11640 → 8730 ps(run#104)

STA が読み出しパスの不足を報告していたので、`dram_clk` の位相を早めれば
書き込み側の余りが読み出し側に 1:1 で移ると考えた。**両方悪化した。**

| | 11640 ps | 8730 ps |
|---|---|---|
| setup write/command | +4.395 | +2.018 |
| setup read | **-2.357** | **-4.585** |
| hold write/command | — | +11.429 |
| hold read | — | +16.021 |

11640 ps に戻した。**トレードのモデルが間違っている**ので、
逆方向の3点目を取るまでこのつまみは動かさないこと。

ただし読み出しパスが -2.357ns で実際に落ちているのは事実で、
**hold 側には 11〜16ns も余っている** — マージンはどこかに存在する。
このつまみでは届かないだけ。

> 位相は量子化されている。VCO は 687.2727 MHz(85.909091 × 8)、
> VCO 周期 1455.03 ps、**1455 ps の整数倍だけが整数 ps になる**。
> `8264 ps` は Fitter に拒否される
> (`Error: PLL Output Counter parameter 'phase_shift' is set to an illegal value`)。
> 既存の 11640 は 8 VCO 周期、17460 は 12。

### 1.4 これまでに外した対策(繰り返さないこと)

- ✗ **CAS レイテンシ 3**(testB22): STA が動かず(-2.408 → -2.357)、実機も不変。
  この制約が測るのは「部品が出してから FPGA が掴むまで」のピン間関係で、CL は無関係。
  CL が変えるのは**いつ出るか**で、**出た後の掴み方**ではない。CL=2 に戻した。
- ✗ **`-max 3.5` への較正**(KFSDRAM が 5.9 を 2.357 外していたので逆算した):
  STA が悪化(-2.408 → -5.222)。5.9 に戻した。
- △ **`sdram_a`/`sdram_ba` の毎サイクルクリアを止めた**(SSO 低減、testB23):
  効果は未証明だが害も無いので残してある。機能は変わらない
  (部品はコマンドと一緒にラッチする。NOP サイクルのアドレス線は誰も見ない)。
  なお **PCXTDEV でも起動音は鳴っていた**ので、「これで直った」という主張は成立しない。

### 1.5 ⚠️ 計測器が実験を汚染した件(2回やった)

`postmon.c` の `guest_peek()` は **`ext_access_request` でバスを奪う**。
testB21 でこれを毎ループ実行したため、BIOS のメモリテスト中に横から SDRAM を叩いていた。

| ビルド | guest_peek | メモリテスト |
|---|---|---|
| testB19 / B20 | **なし** | **通過(MAX 08)** |
| testB21 / B22 / B23 | **あり(毎ループ)** | **失敗(POST 54)** |

現在は `idle_ticks >= 4000 && post_max >= 0x08` でゲートしてある。

**教訓: バスを奪う計測器は、測っている対象を壊しうる。**
観測専用(`post_monitor.sv`)とバスを奪う観測(`guest_peek`)は別物として扱うこと。

なお、ランタイム中に ext ポートを使うのは `st_run`(セルフテスト)と
BIOS ロード時の `bios_access_request` **だけ**で、ディスクサービスは使わない
(`core_top.sv:1795` の `ext_access_request = st_run | bios_access_request`)。
POST 05 の時点ではどちらも走っていないので、`WROTE F000:412E` は汚染ではない。

## 3. 技術知見(これまでのセッションで確定したもの)

1. **rbf_r パッケージ変換は「バイト内ビット順のリバース」(0x6a→0x56)。XOR 0xFF ではない。**
   CI の生 rbf は `FF×128 + 6a 6a 6a 6a 36 f4` で始まり、ビット順反転すると正規形式
   `FF×128 + 56 56 56 56 6c 2f`(SD 内278コアすべてがこの形式)。
   実証: `bitrev(build/b1/ap_core.rbf) == dist/testB1/.../bitstream.rbf_r` が
   **全 1,741,492 バイト一致**(実機 BIOS 動作実績ペア)。XOR 0xFF に読み替えると
   `00×128` 始まりになり Load error。変換コードは `scripts/package.sh`。
   パッケージ手順: `dist/testB1` をコピーして bitstream.rbf_r だけ差し替え(過去実績あり)。
2. **dram_clk は clk_chipset と半周期(180°)逆相。** リードデータの *launch* が negedge 同相
   ということは、**有効窓の中央は posedge** という意味。「逆相だから negedge で取る」は
   逆向きの誤り(testB6 で1ビルド失った)。KFSDRAM の実サンプル点 P+CL+1 posedge に
   合わせるのが唯一の正。導出は §1.1。
3. **KFSDRAM(実績品)の設計値**: CL=2・BL=1・毎サイクルパイプラインREAD・
   リフレッシュは enable_refresh 駆動(バスアイドル時)+ 1024サイクル(23.8µs)強制。
   23.8µs は規格違反だが実機で動く = リフレッシュ間隔は致命要因になりにくい。
4. **自作モデルの教訓(2度やらかした)**:
   - モデルの DQ 駆動は実部品の「次データで置換されるまで保持」を再現すること
     (`sdram_model.sv` はスロット CL-1〜CL+1 の3スロット保持に修正済み)
   - **TB は必ず動作既知の参照(KFSDRAM)も同じ条件で通すこと**。
     参照が落ちるなら疑うべきはモデル/ TB 側
   - 同相クロックのモデルはこの基板では位相が違う。逆相+フライト遅延込みが
     `sim/sdram_board_model.sv`(T_CO=7ns / T_RET=8ns。実測値ではないので過信しない)
5. **SDC は `pcxt-base/src/fpga/core/core_constraints.sdc` が唯一の正**(47行→現在)。
   `apf/apf_constraints.sdc` が `read_sdc` で読む。リポジトリ直下の
   `src/fpga/core/core_constraints.sdc`(185行)は**姉妹プロジェクト由来でビルドされない**
   — PLL インスタンス名が `ic|mp1|mf_pllbase_inst|...` でこの設計には存在しない。
   数値の参照元としては有用(同一基板・同一 SDRAM 部品)だが、そのままコピーしないこと。
6. **STA の "worst-case slack" は制約したパスについてしか語らない。**
   `Unconstrained Input/Output Ports` セクションを必ず見ること。今回 SDRAM 全ピンが
   そこに並んでいた = 解析パス0本。`scripts/check_sdram_paths.tcl` が CI でこれを見張る。
7. **シミュレーション環境**: Docker `pc98-sim` イメージ(Verilator 5.020)。
   `bash sim/run_ph.sh` で tb_ram_ab を ref / mp / mp_kfref の3モード実行。
   CI(`.github/workflows/build.yml`)に全TB+ボードタイミング版を回帰登録済み。
   落とし穴: Verilator 5.020 の `fork/join` は SIGSEGV。コメント内に "verilator"
   という単語を書くとディレクティブ誤解析でエラー。
8. **ビルドは CI 一択**(13〜15分)。ローカル Docker は45分以上かかる(検証済み、使わない)。
   DNS 故障中は `scripts/tools/ghpush2.py` で push(履歴維持)、`getartifact.py <run> <dest>`
   で成果物取得、`ghpoll2.py` で状況(たまにタイムアウトするので `ghlib` 直叩きも可)。
   `diskutil eject /dev/disk4` は今回のセッションでは成功した(以前は権限エラーだった。
   失敗したら Finder をユーザーに依頼)。
9. **`SDRAM_USE_MP`(config.tcl)** = shim 経由で mp を有効化。
   `SDRAM_MP_KF_REF` も追加すると shim の末端が純KFSDRAM に変わる(バイセクト用。
   testB4 の構成。enable_refresh を KFSDRAM に直結しないとリフレッシュ間隔違反になる)。
   コメントアウトで完全にKFSDRAMに戻る(testB3 の構成)。
