# ALM インベントリ — 何が ALM を食っていて、どこから 1,000〜1,500 ALM を空けるか

作成: 2026-11-14 / `docs/SPEED_VS_REAL.md` の対になる文書（「回路へ移すと N ALM」対「Y を削れば M ALM 空く」を並べるため）

この文書は**計測と分析だけ**の記録で、RTL もファームウェアも変えていない。

- **release**: `release5-s31`（HEAD `ba2f7de`、CI #1154、run 43407834027）— `ENABLE_OPNA=1`、`PC98_JTAG` なし、SEED 31
- **release (現行)**: `release7`（HEAD `cd49e11`、CI #1183、run 43732062097）— `ENABLE_OPNA=1`、`PC98_JTAG` なし = main (`a870fc8`) のリリース化。**§0.5 が現行ベースライン**（GDC HW エンジン第 1 段 + 表示モード込み、LAB 空きゼロ）
- **debug**: `combo4-dbg-s29`（HEAD `08bc561`、CI #1155、run 43409212024）— `PC98_JTAG=1`、OPNA なし、SEED 29
- 出典: 各 run の `bitstream` アーティファクトの `output_files/ap_core.fit.rpt`「Fitter Resource Utilization by Entity」と `ap_core.map.rpt`。
- 「**測定**」= fit レポートの値か `scripts/measure_core.sh`（単体合成、quartus_map のみ）の差分。「**推定**」= コード読みからの見積もり。
  `measure_core.sh` の値は単体での見積もりで、設計に組み込んだ値とは一致しない（例: `z86_cache` は単体 1,397、設計内 1,939）。
  したがって削減量は **同じ条件での 2 回の差** だけを使っている。

> **2 つのプロファイルは同じソースではない。** debug は release5 の z86 execute のトリム
> （`d411dbb`〜`d3753ef`、§4.3）を含まず、OPNA を外して JTAG 一式を入れている。
> モジュール単位の比較は「同じモジュールがだいたいどれだけか」を見るためのもので、release − debug の差を
> 「デバッグの費用」と読んではいけない（デバッグ専用の費用は §4.4）。

## 0. 要約

> **2026-11-16 追記**: 現行ベースラインは §0.5 の release7（GDC エンジン第 1 段 + 表示モード込み、
> **ALM 17,637 / LAB 1,848 = 空きゼロ**）。この節の数値は release5 時点のまま残している。

**問い**: GDC 描画の全部（直線・円弧・矩形・WDAT・テキスト）を回路へ移す（推定 900〜1,500 ALM、
`docs/GDC_HW_ENGINE.md` / `gdc-line-hw`）。release にはその空きがない。どこから 1,000〜1,500 ALM を空けるか。

**現状（release5）**: ALM needed 17,267 / 18,480、**LAB 1,815 / 1,848（空き 33 LAB ≈ 330 ALM）**、
**M10K 308 / 308（空きゼロ）**、DSP 12 / 66。今の密度は needed 9.5 ALM / LAB なので、
GDC エンジン 900〜1,500 ALM ≈ 95〜158 LAB。手持ちの 33 LAB を引くと **600〜1,200 ALM を空ける必要があり、
シード依存の余裕 30 LAB 程度を足して 1,000〜1,500 ALM** が目標になる。

**ALM を食っている上位 10（release、そのブロック自身の合計）**

|---:|---|---:|---|

| 3 | OPNA（`pc98_opna` + jt12） | 1,460 | うち ADPCM-A（リズム）約 450 |

**空けられる量（release）**

| 区分 | ALM | 根拠 |
|---|---:|---|
| A. 振る舞いを変えないトリム（§4.1 の A1〜A9） | **約 600〜900** | ほぼ推定 |
| A0. GDC を回路へ移すと要らなくなる FW 用の配管（§4.1 A0） | **約 150〜250** | 推定。エンジン費用からの相殺 |
| B. 機能・性能を落とす（要判断、§4.2） | **最大 約 2,100**（下の表の合計） | 主要なものは測定 |
| 　B1 OPNA ADPCM-A（リズム音源 + FDD 駆動音キット）をやめる | **559** + M10K 38 | 測定 |
| 　B2 z86_cache の書き込み結合（WCOMB）をやめる | **398** | 測定 |
| 　B3 gvram_seq の RMW 行バッファ一式をやめる（先読みだけなら 83） | **551** | 測定 |
| 　B4 バスマウス（`pc98_busmouse` + `pc98_mouse_src`） | **246** | fit 実測 |

**計画（§5）**: まず A（約 600〜900）と A0（150〜250、エンジンと同時）で **750〜1,150**。
それで足りなければ **B1（559、M10K 38 個も空く）** を最初の判断候補にする。
B1 は GDC エンジンが M10K を必要とする場合（円弧の表 7 個など）に M10K を返せる唯一の大きな候補でもある。

SPEED_VS_REAL.md §5 の回路移設費用との並び:

| 回路へ移す（SPEED_VS_REAL §5） | 推定 ALM | | 削って空ける（本書） | ALM |
|---|---:|---|---|---:|
| GDC 描画エンジン | 900〜1,500 | ← | A + A0（振る舞い不変） | 750〜1,150 |
| ディスク転送回路 | 150〜300 | ← | B4 バスマウス or B3 の先読み + A の残り | 83〜246 |
| FDD 回転位相 | 100〜200 | ← | B5 クロスフィード（約 100） | ~100 |
| OPNA BUSY | 40〜80 | ← | （B1 を選ぶなら ADPCM 側の BUSY は不要） | — |
| **合計** | **1,190〜2,080** | | **A + A0 + B1** | **1,310〜1,710** |

## 3. RAM 推論の点検（map.rpt）

両プロファイルの `ap_core.map.rpt` を `276004 / 276007 / 276014 / 276020 / 276027` と
「asynchronous read」で全モジュールについて探した結果:

- **RAM にならなかった配列（Info 276004 "inappropriate RAM size"）は 3 つだけで、どれも小さい**:
  `sdram_mp.open_row`（4 バンク × 行アドレス）、jt12 `jt12_pm` の `lfo_sh1_lut` / `lfo_sh2_lut`（小さな ROM）。
  RAM 化しても数 ALM。**「RAM にし損ねた大きな配列」は存在しない。**
- **Warning 276020「Pass-through logic has been added」** — read-during-write の新旧一致のために
  Quartus が比較器と迂回 mux を足した RAM。release で 8 個:
  `core_top.romfifo`（2048×42）、`picorv32.cpuregs` ×2（32×32 相当）、`pc98_gvram_seq.stg`（16×16）、
  `floppy` の `simple_fifo.mem`（2048×8）、`glyph_rowbuf.hold8`、`kbd8251.kq`、`pocket_keyboard.queue`。
  同一アドレスの同時読み書きが設計上起きないなら `no_rw_check` で外せる（候補 A4）。
- **276027（デュアルクロック RAM）** は tvram / rowbuf / gvram_display / key_cfg / sprom。追加ロジックはない。
- `pf_buf`（cpu_bus_bridge の MLAB）は **debug にだけ** ある。release は `pf_disable` が定数 1 なので先読み窓ごと畳まれている。
- **デバッグ用カウンタの release 残留はない。** `dbg_crt`・`dbg_scsi`・`fdc_dbg_*`・`z86 dbg_regs` などは release で
  読み手がなく、map.rpt の「Connected to dangling logic」で消えている（`crt_fire_n`、`scsi_rom_rd_count`、`dbg_command` は
  map.rpt に名前すら残らない）。core_top の JTAG ブロック（1329〜2432 行）は `ifdef PC98_JTAG` の中。
  → 「release に残ったデバッグ回路を消す」で取れるものは**ほぼない**。
